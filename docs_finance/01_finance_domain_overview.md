# 재무 도메인 기획 개요 (Finance Domain Overview)

> **문서 버전**: v2.0 (시뮬레이션 기준 전면 갱신 — index.html / recon.html 반영)
> **작성 기준**: docs_finance/guide.md, index.html, recon.html, ADR-002, ADR-011, ADR-012
> **최종 갱신일**: 2026-04-09

---

## 1. 기획 목적

본 문서는 Balhea ERP 재무 도메인의 **1차 구현 범위**를 정의한다.

재무 도메인은 계약(Contract), 수급(Sourcing), 시스템(System) 도메인과 연결되어  
발주 이후의 **비용 인식 → 지급 요청 → 지급 승인/집행 → 대사/정산조정** 흐름 전반을 관리한다.

---

## 2. 도메인 위치 (전체 ERP 관점)

```
[시스템 도메인]                 [재무 도메인]
  parties ──────────────────────► costs / invoices / payables / payments
  documents + document_links          ↑             ↑
  audit_changes / activity_logs       │             │
                                      │             │
[계약 도메인]                         │             │
  projects → orders ─────────────────► receivables (AR) → receipts (입금 원장)
              (order_lines)           (receivable_order_links로 1:1 연결)
                                      │
[수급(구매) 도메인]                   │
  sourcing_cases                      │
  sourcing_case_lines                 │
  purchase_orders ──────────────────►po_cost_links → costs (AP)
  po_lines
```

**재무 도메인의 핵심 역할**: 수금(AR)과 지출(AP) 양방향 정산을 독립적으로 관리하되,  
`sourcing_case_lines`(조달목적 정본)와 `orders/order_lines`(납품 약속) 등 원거래 파일과의 매핑 흔적을 항상 유지한다.

## 3. 핵심 설계 원칙 (참조: ADR-002, ADR-011, ADR-012)

### 3.1 D3 분리 원칙 (Cost / Payable / Payment)

| 개념 | 엔티티 | 역할 |
|---|---|---|
| 비용 발생 | `costs` | "얼마에 무엇을 샀는가"의 사실 원장 |
| 지급 요청(청구) | `invoices` | 거래처가 발행한 청구 문서 컨테이너 |
| 지급 단위 | `payables` | 내부 승인·보류·분할 지급의 업무 단위 |
| 실지급 | `payments` | 돈이 실제로 나간 결과 기록 |

> **불변식**: Invoice는 지급 단위가 아니다. 지급은 Payable 단위로 이루어진다.

### 3.2 PO 1건 = Cost 1건 (ADR-012)
- `po_cost_links`를 통해 PO와 Cost를 1:1 연결
- 정산 단위를 단순하게 유지하여 운영 오류 방지

### 3.3 비용 귀속의 정본은 `cost_allocations` (ADR-009)
- `po_cost_links` 등 링크 테이블은 UI 탐색 편의용
- 원가/정산 계산은 반드시 `cost_allocations` 기준

### 3.4 문서 허브: `documents` + `document_links`
- 모든 증빙(거래명세서, 세금계산서, 이체 영수증 등)은 `documents`에 단일 저장
- 연결만 `document_links`로 다대다 처리

### 3.5 마이너스 Cost(상계) 처리 원칙 *(v2.0 신규)*
- `costs.amount < 0`인 비용은 **상계(Offset) 항목**으로 취급한다.
- 지급요청관리(AP) 및 정기결제관리 상세의 "상계 처리 내역 불러오기" 버튼을 통해 해당 거래처의 미할당 마이너스 Cost를 조회하고, payable에 할당(차감)할 수 있다.
- 상계 적용 항목은 빨간색 `[×]` 버튼으로 개별 제거 가능하며, 제거 시 차감 금액이 즉시 복원된다.

## 4. 1차 구현 범위 (현행 시뮬레이션 기준)

아래 업무 영역이 현재 시뮬레이션(`index.html`, `recon.html`)에 구현되어 있다.

| 번호 | 업무 영역 | 구현 수준 |
|---|---|---|
| **②** | 지급관리 (Accounts Payable, AP) | ✅ 직접 구현 핵심 |
| **②-1** | 정기결제 관리 (Periodic Payment Management) | ✅ 직접 구현 핵심 *(v2.0 신규)* |
| **③** | 지급내역 관리 (Payments History) | ✅ 직접 구현 핵심 (Read-only 증빙 확인) |
| **④** | 미지급 관리 (Unpaid Monitoring) | ✅ 직접 구현 핵심 (리스크 거래처 감시) |
| **⑤** | 대사·리콘실리에이션 | ✅ 직접 구현 핵심 (세금계산서 대사 중심) |
| **⑨** | 보고·분석·대시보드 | ✅ 직접 구현 핵심 (실무형 운영 대시보드) |
| **⑪** | 정산조정관리 | ✅ 직접 구현 핵심 |
| **⑥** | 조달·매입·발주 | 🔶 부분 반영 (재무 연결 역할 중심) |
| **⑦** | 증빙·문서관리 | 🔶 부분 반영 (재무 흐름 필수 증빙만) |
| **⑩** | 권한·감사·통제 | 🔶 부분 반영 (지급 승인/처리 권한 분리) |

> **1차 시뮬레이션 범위**: AR(수금) 흐름은 아키텍처 설계에는 포함되어 있으나, 현재 대시보드 및 지불/대사 시뮬레이션 화면에서는 제외되어 있습니다. (Phase 2 확장 범위)

## 5. 핵심 업무 플로우 (Big Picture)

```
[발주서(PO) 기반 흐름]

PO 확정
  │
  ▼
① 비용 인식 (costs + po_cost_links)
  │
  ▼
② 거래처 청구서 수신 → 지급요청(payables) 등록
  │
  ├──[일반 거래처]──► 지급요청관리(AP) 리스트에 표출
  │
  └──[정기결제 등록 거래처 + APPROVED 상태]──► 정기결제 관리 탭으로 자동 격리
  │
  ▼
③ 지급 단위 생성 및 승인 요청 (payables: CREATED)
  │
  ▼
④ 대표 최종 승인/반려 (payables: APPROVED 또는 REJECTED)
  │
  ▼
⑤ 지급 실행 [재무 담당자] (payments: TRANSFER 중심)
  │
  ▼
⑥ 세금계산서 수신 → 대사 (tax_invoices ↔ payments)
  │
  ▼
⑦ 불일치 발생 시 → 정산조정 (settlement adjustments - 대표 승인 필수)
```

## 8. 주요 서브 도메인별 상세 요건

### 8.1 보고·분석·대시보드 (Reporting & Analytics)
- **목적**: 실시간 재무상태를 한눈에 파악하고 상세 화면으로 빠르게 진입할 수 있게 한다.
- **핵심 업무**: 핵심 대시보드 설계·운영, 표준 리포트 제공, 드릴다운(상세조회) 연결, 알림·경보, 사용자·역할별 뷰 제공
- **부분 반영 범위**: 재무 대시보드, 업무현황 카드, 업무메뉴 바로가기, 상세 리스트 드릴다운 연결
- **현재 범위 내 원칙**:
  - 이번 재무 대시보드는 통계형 분석 화면이 아니라 실무형 운영 대시보드로 설계한다.
  - 상단에는 **지급처리 대기, 미지급 건수, 미지급 금액, 미대사 건수, 정산조정 대기** 5종 지표를 카드로 보여준다.
  - 본문(Zone C)은 지급 대기(AP), 미대사 큐(Recon), 미지급 위험 모니터링(Unpaid) 3개의 큐를 고밀도 3-Column 뷰로 동시 배치한다.
  - UI 방대함을 제어하기 위해 프론트엔드 아키텍처를 **지급/미지급 모듈(index.html)**과 **대사/정산조정 모듈(recon.html)**로 분할하되 라우팅으로 심리스하게 연결한다.
  - **사이드바 구조**: **대시보드, 지급요청관리(AP), └─ 정기결제 관리(하위 탭), 지급 내역 관리, 미지급 관리, 세금계산서 대사, 정산 조정 관리** 7대 메뉴 체계 운영.
    - **정기결제 관리** 탭은 '지급요청관리' 메뉴 클릭 시에만 사이드바에 표출되며, 다른 메인 카테고리 클릭 시 자동으로 숨겨지는 동적 서브 메뉴이다.
- **비고**: 현금흐름, 미수 연령, 프로젝트 손익, 자산 상각 등 분석형 대시보드는 후속 확장 범위로 본다.

### 8.2 권한·감사·통제 (Controls & Audit)
- **목적**: 재무 관련 작업의 책임소재를 명확히 하고 내부통제를 통해 오류·부정·감사리스크를 예방한다.
- **핵심 업무**: 역할 기반 권한 설계 및 관리, 결재 임계값 규칙 설계 및 운영, 변경이력(감사로그) 수집 및 조회, 권한 위임/대결 관리, 감사 대응 지원
- **부분 반영 범위**: 지급 승인/처리 권한 분리, **대표 승인 및 반려 기능 조건부 노출**, 재무는 지급 실행 담당
- **현재 범위 내 원칙**:
  - 재무담당자(1인)와 대표는 **동일한 화면**을 공유한다.
  - 대표 로그인 시에만 추가 UI 요소가 조건부 노출된다:
    1. **헤더 결재 드로어 (🔔)**: 결재 대기 건수 뱃지 + 클릭 시 AP·정산조정 승인대기 목록
    2. **AP 리스트 인라인 버튼**: CREATED 상태 행에 `[승인]` `[반려]` 버튼이 해당 행에 직접 표출
  - 재무 담당자는 실무 기안 및 지급 실행을 담당하고, 대표는 위 두 가지 진입점을 통해 최종 승인/반려한다.
- **비고**: 상세 감사로그, 권한이력, 대체결재, 긴급결재 등은 후속 확장 범위로 본다.

### 8.3 정기결제 관리 (Periodic Payment Management) *(v2.0 신규)*
- **목적**: 대한통운, 마이넌 배관시스템 등 월 단위 정기성 거래처를 별도 격리·관리하여 일반 지급 대기 큐(AP)의 혼선을 방지하고, 익월 특정일(예: 10일)에 일괄 처리한다.
- **핵심 로직 (자동 분류)**:
  - 재무담당자가 특정 거래처를 '정기결제 대상'으로 등록하면, 해당 거래처의 **APPROVED 상태** payables는 일반 AP 리스트에서 자동으로 제외되고 정기결제 관리 탭으로만 집결.
- **UI 구조 (Split-View)**:
  - **좌측 패널 (30%)**: 정기결제 등록 업체 목록 + 신규 등록 인풋
  - **우측 패널 (70%)**: 선택된 거래처의 전체 지급요청 리스트(AP와 동일 레이아웃) + 하단 집계 및 상계 처리 영역 + 월 마감 지급 실행 버튼
- **상계(Offset) 처리**: 우측 하단의 "상계 처리 내역 불러오기" 버튼을 통해 해당 거래처의 마이너스 Cost를 불러오고, `[×]` 버튼으로 개별 제거.
- **최종 실행**: 리스트 최하단의 "지급 실행 (Payments 결제 모듈)" 블록에서 일괄 지급 실행.

### 8.4 정산조정관리 (Settlement Adjustment Management)
- **목적**: 원거래 이후 발생한 환수, 반환지급, 추가지급, 추가수금 등 후속 조정거래를 독립적으로 관리한다.
- **포함 업무**: 정산조정 관리 리스트, 정산조정 상세 화면, 정산조정 처리, **정산조정 처리에 대한 대표 승인/반려 로직**
- **이번 범위**: 직접 구현 핵심 범위
- **정산조정 유형 예시**: 환수, 반환지급, 추가지급, 추가수금, 기타조정
- **정산조정 원칙**:
  - 독립 메뉴로 운영하되, 지급내역 화면에서 `[+ 정산조정(환수 등) 발의]` 버튼을 통해 화면 이탈 없이 모달 팝업으로 즉시 발의 가능.
  - 발의된 데이터는 localStorage를 통해 정산조정 리스트(recon.html)에 실시간 동기화.
  - 후속거래는 반드시 원거래 `origin` ID와 함께 기록되며, 클릭 시 원거래 화면(`?menu=ap&search=ID`)으로 즉시 추적 이동 가능.
  - 자금 변동이 수반되는 조정은 **대표의 명시적 승인**을 통해서만 최종 확정.
