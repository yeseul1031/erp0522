## 1. 배경 및 핵심 문제

### 운영 구조

| 항목 | 내용 |
|------|------|
| 프로젝트당 담당자 | 1명 |
| 발주 흐름 | 견적 수령 → 가격 비교 → 발주서 작성 → 대표 승인 요청 |
| 발주서 수 | 프로젝트 1건당 거래처 수만큼 여러 개 생성 가능 |
| 협업 | 해외구매팀은 별도 시스템 사용 (이 문서 범위 외) |

### 발주서 머지(통합) 발생 이유

대표가 승인 검토 시, **같은 거래처에 발주하는 건이 여러 담당자에게서 올라오면** 묶어서 발주하도록 지시. 수량이 많을수록 단가·배송비 할인 협상 가능.

- 발생 빈도: **거의 매번 (50% 이상)**
- 주요 거래처 수: **70~80개 이상**
- 머지 기준: 같은 거래처면 물품 종류와 무관하게 일괄 통합 검토

### 현재 구조의 문제점

```
현재 프로세스
───────────────────────────────────────────────────────
김철수  → 발주서 A (볼펜 50개, 서산베어링)  ─┐
이영희  → 발주서 B (볼펜 50개, 서산베어링)  ─┘→ 대표: "합쳐서 발주해"
                                                    ↓
                              이영희 발주서 B 삭제
                              김철수 발주서 A에 이영희 발주 라인 추가
                                                    ↓
                         오너십: 김철수만 남음 / 이영희는 ERP에서 발주 내역 가시성 상실
                         → 이영희는 본인 물품 입고 여부 ERP에서 확인 불가
                         → 김철수가 전화로 "니 물건 들어왔어" 수동 안내해야 함
```

**근본 원인:** ERP 발주서 문서를 프로젝트 단위로 관리하다가, 실제 운영에서 거래처 단위로 머지가 발생하면 오너십이 단일화되어 기존 담당자의 데이터 추적 가시성이 단절됨.

## 2. 데이터 모델 변경사항

### 발주 라인(`po_lines`) 원본 연결 유지 (신규 필드 추가 불필요)

기존 안에서는 정보 유실 방지를 위해 발주 라인에 `원담당자ID`, `원프로젝트ID`를 새로 추가하려 했으나, ERP 데이터 통합 정책에 따라 **중복 필드는 일절 추가하지 않습니다**.
두 개의 발주서를 하나의 `purchase_orders` (헤더)로 통합하더라도, **각 `po_lines`는 기존의 `sourcing_cases` 및 `order_lines` 기반 참조를 물리적으로 그대로 유지**하게 됩니다.

- `po_lines` → `sourcing_cases` → `order_lines` → `projects` 연쇄 조인을 통해 **원래 담당자(`assignee_principal`)와 소속 프로젝트 정보에 100% 접근 가능**하므로 무결성이 보존됩니다.

### 거래처 테이블(`parties`) 관리 필드 추가

마감일 설정을 통해 발주 타이밍 불일치를 해소합니다. 단, 오픈마켓(쿠팡 등) 자체가 통째로 단일 Party일 경우 일상 비품 상신까지 모두 마감일에 묶여버리는 치명적 부작용이 있습니다. 따라서 **B2B 직거래 벤더(Vendor) 파티에 한정하여 적용**합니다.

```text
parties (거래처 파티)
├── ... (기존 필드)
├── pt_order_deadline_day   ★ 신규 (예: 'TUESDAY') - 직거래 벤더 한정
├── pt_order_cycle          ★ 신규 (매주 / 격주 / 월1회 등)
└── pt_urgent_order_allowed ★ 신규 (Y/N) - 긴급 상신 모드 지원 여부
```

### 머지 실행 시 동작

1. 사라지는 대상 발주서(B)의 발주 라인(`po_lines`)들이, 기준 발주서(A)의 헤더 하위(`po_sn` FK 변경)로 통합 이동됨.
2. 이동된 `po_lines`들은 원래 속해있던 `sourcing_cases`와의 링크를 그대로 유지함.
3. 발주서 헤더 B(`purchase_orders`)는 **삭제가 아닌 `통합됨(MERGED)` 상태로 아카이브**하여 원본 이력 보존.
4. 원담당자(이영희)에게 "당신의 발주 요청이 PO-XXX 내역으로 통합되었습니다" 알람 자동 발송.

## 3. 역할별 플로우

### 3-1. 전체 흐름 개요

```mermaid
flowchart TD
    A[담당자: 발주서 작성] --> B{B2B 직거래 벤더 & 마감 주기 설정 여부}
    B -->|설정됨| C[마감일까지 해당 거래처 대기 큐에 등록]
    B -->|미설정 / 오픈마켓| D[즉시 대표 승인 큐 진입]
    C -->|긴급 발주 플래그 ON| E[사유 명시 후 즉시 대표 큐 진입]
    C -->|마감일 도래| F[같은 거래처 발주 묶음 일괄 대표 큐 진입]
    D --> G[대표 승인 판단 화면]
    E --> G
    F --> G
    G --> H{동일 거래처발 복수 묶음?}
    H -->|Yes| I[통합 검토 — 오너 추천 및 통합 승인]
    H -->|No| J[개별 단순 승인 또는 반려]
    I --> K[머지 실행: po_lines를 단일 새 PO 산하로 이동]
    K --> L[통합 발주서 승인 완료]
    J --> L
    L --> M[거래처 최종 PO 문서 발송]

    N --> O[전체 라인 대상: 발주 오너(김철수)에게 종합 알림]
    N --> P[해당 물품 한정: 식별된 원담당자(이영희)에게 자동 알림 분배]
```

## 4. 대표자 승인 화면 상세

### 4-1. 승인 대기열 리스트 화면

| 영역 | 내용 |
|------|------|
| 글로벌 필터 | 전체 리스트 / 통합 승인 권장(묶음) 필터 / 벤더(Party)별 |
| 스마트 그룹핑 | B2B Party(`pt_sn`) 기반 동일 거래 건 적발 → 주황색 연결선으로 배지 묶음 노출 |
| 요약 카드 | 내부 문서번호, 프로젝트(계약) 정보, 대상 벤더, 기안자 식별, 취합 건수, 금액 통계 |
| 강조 배지 | 병합 가능 세트에 "통합 심사 요망" 라벨 강제 노출 |

### 4-2. 발주서 통합 스펙 뷰어 화면

**단독 건 클릭 시:** 평범한 승인/반려 모드 진입.

**통합 묶음 클릭 시:** N개의 발주 내역을 좌우 횡단으로 비교 나열하는 와이드 패널 전환.

| 영역 | 기능 설명 |
|------|------|
| 상단 분석 바 | 중복 품목 탐지 및 발주 최적화 가이드 멘트 노출 |
| 파사드 비교 | n개의 원본 담당자, 파생 프로젝트명, 각개 총 물동량과 비용 노출 |
| 헤더 오너 선정 | 단일 발주 통합 후 PO 책임을 질 '통합 구매담당자' 라디오 볼 버튼 지정 |
| 통합 목록 프리뷰 | 조인을 통한 원본 담당 라벨(`_principal`)이 붙은 채로, 중복 물품 합산 또는 분리 리스트 조망 가능 |
| 결재 트랜잭션 | 항목별 각각 승인 처리 / **일괄 병합 승인(MERGE & APPROVE)** / 전체 반려 |

### 4-3. 통합 후 자동 시스템 처리 프로시저

```
1. 이영희(기존) 발주서의 하위 라인들(`po_lines`)을 떼어내어 김철수 통합 PO(`purchase_orders`)로 소속 FK(`po_sn`) 마이그레이션 변경.
2. (단독 `sourcing_cases` 링크는 생존시킴으로써 영원한 이력 보장 제공).
3. 원본 발주서 껍데기는 삭제(`DELETE`)되지 않으며 'MERGED' 코드로 아카이브 기록 보유.
4. 이중 푸시(기존자 및 통합 리더) 통합 알람 즉시 전송.
5. 김철수 이름 앞단의 통합 PO 코드로 최종 승인 종결.
```

### 4-4. 긴급 상신 UI 표출

- 리스트 썸네일에 빨간 "긴급(URGENT)" 텍스트로 가시적 구별.
- 상세 열람 시 입력된 예외 사유 기록이 `activity_logs`와 연동되어 최상단에 고정 표시됨.

## 5. 구매담당자 (통합 오너) 화면 경험

### 5-1. 발주 기안기(폼) 시작 화면

| UI 콤포넌트 | 기능 동선 |
|------|------|
| 벤더 지정 드롭박스 | 거래선을 지정하자마자 B2B 정책을 조회, 적용 대상이면 해당 마감 타이밍과 D-DAY 즉석 통보 |

| 긴급 바이패스 스위치 | Toggle ON 발동 시 필수 사유 필드 팝업 오픈. 작성 시 풀에서 탈옥하여 즉각 큐 상신 |

### 5-2. 통합 후 'PO 관리 디테일' 패널

| 영역 | 구성 내용 |
|------|------|
| PO 메타 헤더 | 본인 이름(오너), 확정 발주일, 종합 외화/한화 비용 합계, 보라색 '병합된 이력 있음' 라벨 |

| 자동 고지 배너 | "통합 아이템 포진됨. 실물 화물 도착 후 입고(RECEIPT) 트랜잭션 시 조인 담당자들에게 자동 전파됩니다." |
| 하이브리드 목록 | 본인 태생 오더건(투명 배경) / 편입 탑승 건(회색 코팅) UI 시각 분리 |
| 입고(`inventory_operations`) 버튼 | **자신 몫의 라인에 대해서만** 재고 작업 생성 트랜잭션 모달 활성화 |
| 꼬리물기 연동 | 결제(지급) 대상 추출 / 커로우팅 거래처 메시지 로그 센터 / 재고 로그 타임라인 조회 |

## 6. 연관담당자 (원본 기안자) 화면 경험

### 6-1. 마이 파이프라인 (내 발주 리스트) 뷰어

**강력한 조인 탐색 쿼리 기반 구조 변경**

```
이전 한계: 본인 명의 계정(PO 헤더의 assignee FK)으로 된 것만 단순 출력
신규 구조: 헤더 권한 확보된 PO 건들 + UNION + [내 sourcing_cases 연계 po_lines]가 탑재된 머지 PO 건 추적
```

| 카드 콤포넌트 선명도 | 좌측 인디케이터 컬러 | 상세 권한 |
|-----------|-----------------|------|
| 독립적 내 발주 오더 | 초록 (Green) | 전체 문서의 운영 총괄 권능 |
| 셋방 연관 발주 오더 | 보라 (Purple) | PO 결제 및 총괄 제어 불가. 단, 나의 아이템 라인(`po_lines`) 제어 권한만 살아있음 |

| 편의 영역 | 내용 |
|------|------|
| 세부 필터링 | 전체 / [독립 내 발주] / [연관 탑승 발주] / 미결/완결 필터 |
| 상단 점멸 배너 | 미검수(입고 도래) 물품 대기 중일 때 강력 환기 유도 팝업 |
| 연관 카드 디자인 | 현재 대리 오너명 명시 + 내 자산 품목만 추출하여 간이 표시 |
| 재고 원장 생성 액션 | **오직 본인 소속 아이템에 한해** `inventory_operations` 신규 추가 모달 개방 |

### 6-2. 연관(셋방) 발주서의 접근 통제 경계선

| 시스템 내 통제 항목 | 인가 범위 (연관 담당자) |
|------|------|
| PO 메타 문서 전체 조회 | 읽기 전용 모드 스위핑 (단가 확인용) |
| **물품 입고 작업 이력 누적** | **가능** (수량/일자 컬럼 직접 UPDATE 우회 원천 금지, 트랜잭션 추가만 100% 필수) |
| **재고 입고일 통제** | **불가** (날짜 강제 세팅 불가능. 실제 작업(operation)이 완료 기록되는 시각으로 대체) |
| 품목별 추가 메모 | 가능 (비고 로그 누적용) |
| 물품 추가 및 라인 삭제 | 완전 통제 (불가) |
| 대금 징수/결재 상신 | 완전 통제 (불가, 헤더 오너만의 전유물) |
| 벤더와의 딜리버리 협의 | 완전 통제 (불가, 일관성 유지) |

### 6-3. 지능형 자동 후크 발송 룰셋

- **헤더 오너(김철수):** 통합 PO 내부 전체를 관통하는 하위 `inventory_operations(RECEIPT)` 트랜잭션 건수 누적마다 총괄 로그 푸시 수신.
- **원본 라인주(이영희):** 본인 할당 라인 소속 물품의 시스템 바코드/상태 등 실물 인수 판별 로직 추가 시, 제한적 "라인 물량 15건 실물 입고 검수 준비!" 자동 멘트 푸시 수신.

## 7. 다이나믹 벤더(Parties) 마감 주기 제어 모듈

### 7-1. 비즈니스 적용 필요성

기안자들의 주관적 타이밍 분산 상신으로 촉발되는, 하루 이틀 단위의 배송/포장비 손실 기회 극복.

- **원인:** 실무 부서별 편차 높은 상신으로 도매 업체로 다발적 조각 오더 전송 됨.
- **개선안:** B2B 직거래 거점 거래처(`pt_sn` = Vendor/Distributor 성격)에 정기 발주요일을 잠궈두고 모아서 대표자 통제 라인으로 집입.

### 7-2. 작동 모커니즘

```
1. 담당자 기안 전송 단계 (Parties 유형 방어 검증)
        ↓
2. [오픈마켓(플랫폼)이 아님 + 요일 마감 룰 적용됨] 판단 시 락인 풀에 대기
        ↓
3. 시스템 데몬이 마감 시각 브레이크를 체크 → 마감 시 일괄 묶음으로 대표 대기열에 자동 덤프 제출
        ↓
4. 대표자는 동일 벤더가 쏠린 것을 목격, 단일 협상력 우위를 쥔 채 '통합 머지 승인' 구사.
```

### 7-3. 데드라인 예외 회피

- 전장의 비상상황 감안, 실무자가 **긴급 상신용 토글 액션**으로 락 풀을 탈출.
- 즉각 사유를 기입하면, 그 흔적이 남은 채 병합 대상에서 제외하고 대표단에 즉시 돌진.
- 마스터 어드민 단에서 Party별 "아예 긴급 회피 원천 불허" 차단벽 설정 가능.

### 7-4. 마감 컨트롤 거버넌스

| 롤 스펙 위치 | 거래처 파티 설정 (`parties`) | 긴급 패스룸 제어 | 대기 카운트 현황 조회 |
|------|-------------------------|------------|------------|
| ERP 최고 관리자 | 전면 세팅 개방 | 전면 통제가능 | 열람 가능 |
| 매입 소싱 담당자 | 수정 락(불가) | 수정 락(불가) | 뷰만 가능 |
| 최고 승인 결재자(오너) | — | — | — |

### 7-5. B2B 파티(거래처) 주기 모니터링 콘솔

| 데이터 컬럼 | 표시 내용 로직 |
|------|------|
| 지정 B2B 거래 명칭 | 플랫폼, 개인 사업자 등 잡다한 풀을 배제한 순수 B2B 벤더망만 리스트업 |
| 정기 셰이핑 타임 | 예시 값: 수요일 / 무방비 상태(주황색 징표) |

| 긴급 바이패스권 | 허가(Permit) / 회수(Block) 상태 |
| 대기 중 화물량 카운트 | 멈춰있는 큐 내 라인수 합산 추이 |
| 넥스트 오더 데이 | 실시간 캘린더 연동 타임스탬프 |

## 8. 최적화 개발 가이드 및 DB 지시서

### DB 컴파일 DDL 표준안 (가이드라인 100% 매칭)

```sql
-- 1. 발주 라인: 반드시 'po_lines'를 지향하며 약어(pol)를 엄수함.
-- [주의 금지사항]: original_manager_id 나 origin_p_sn 따위의 
-- 정보 파편화 중복 컬럼 생성을 강력하게 금지함. 조인 무결성으로 이겨낼 것.

-- 2. 대상 결제선 거래처: vendors 테이블명이 아닌 'parties' 파티 테이블을 통해 다룸.
-- 파티 내 직거래 B2B 용 제어 컬럼만 엄선하여 확충.
ALTER TABLE parties
  ADD COLUMN pt_order_deadline_day   VARCHAR(10) NULL,  -- ENUM급 표기: 'MONDAY', 'TUESDAY'
  ADD COLUMN pt_order_cycle          VARCHAR(20) NULL,  -- ENUM급 표기: 'WEEKLY', 'BIWEEKLY'
  ADD COLUMN pt_urgent_order_allowed BOOLEAN DEFAULT TRUE;
```

### 아키텍처 및 시스템 화면 분기 변경 지서

| 엔지니어링 항목 | 실천 변경 가이드 및 제약 사항 |
|------|----------|
| **가시성 획득 쿼터** | 내가 작성자인 PO + 내가 관여된 sourcing_cases가 하위 po_lines 조인으로 얽힌 타깃 통합건 (UNION) 복원 |
| **UI 차별 컴포넌트** | 꼽사리 건에 대해 시각적 구별 배지(보라색) 및 직관적 오너 노출 추가 컴포넌트 개발 |
| **재고 조작 원천차단** | 화면상 숫자를 쳐서 물량을 입히는 행위를 API단에선 **`inventory_operations(RECEIPT 타입)` 작성 트랜잭션**으로 우회 변환하여 적재해야 함. |
| **통합 컨트롤러 구축** | 승인 리스트에 `pt_sn`(파티값)이 완전히 겹치는 서브 PO들의 합본 어그리게이터 모듈 조립 |
| **FK 스왑 엔드포인트** | 결재권자가 머즈 앤 어프로브 쏠 때, 흡수되는 문서들의 `pol_po_sn` FK를 주인공의 `po_sn` 값으로 마이그레이션 실행 |
| **필터 체인 수립** | 마감 설정 로직 시 오픈마켓이나 개인 비용 청구용 Party(`_pt_type` 등을 검사)는 무조건 데드라인 체인에서 제외되도록 예외 처리. |

### 백그라운드 후크 푸시 발주 표

| 캡처 트리거 이벤트 | 타겟 페이로드 마이닝 방식 | 노출 알맹이 내용 |
|--------|------------------|-----------|
| **RECEIPT 누적 발생** | 해당 PO 전체(`po_lines` 통괄) 소유권자인 헤더의 `assignee_principal` | 현재 발주 문서 전체의 괄목할 재고 입고율 안내 |
| **내 아이템 한정 입고액** | 타 라인 배제, 상태 변화를 맞은 물품만의 `sourcing_cases` 연쇄 딜레이 원 소유자 식별 | "해당 Item의 해당 QTY 만큼 부분 입고 실측 됨" |
| **머지 선고 포고** | 합병 스왑 트랜잭션 도래 직후 서브 라인 관계자(`_principal`) 모두 색출 | "승인 간섭 통보: 통합 PO 번호[XXX] 참조로 편승 처리 완료 안내" |
| **데드라인 발사 12H 전** | 파티 큐(Queue) 룸 안에 서스펜딩된 PO 라인 소속 주주 전원 다지정 | "긴급: 명일 마감 큐 일괄 발송 예고" |
