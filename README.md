# ERP Data Guide

이 저장소는 **ERP 데이터 구조(DDL)와 운영/설계 문서의 정본(Source of Truth)** 을 관리한다.
서비스 UI, IA, Wireframe이 아직 확정되지 않은 상태에서 **데이터 중심으로 먼저 설계**하는 것을 전제로 한다.

---

## 1. 이 저장소의 역할

- ERP 데이터 모델(DDL)의 **현재 정본** 관리
- 데이터 설계의 **운영 가이드 / 설계 맥락 / 결정 기록** 관리
- 외부 설계 도구와의 협업 시 **맥락 손실 방지용 기준점**

---

## 2. 디렉토리 구조 규칙 (정본)

```text
erp-data-guide/
├── ddl/        # DDL 전용 (CREATE TABLE 등 스키마 정의)
├── docs/       # 운영/설계 문서
├── adr/        # Architecture Decision Records (ADR)
└── README.md   # 이 문서
```

---

## 3. DDL 파일 네이밍 규칙

- DDL 파일은 반드시 `erp_*_schema.sql` 형식을 사용한다.
- 파일명에는 **버전을 포함하지 않는다**.
- 예시:
  - `erp_core_schema.sql`
  - `erp_finance_schema.sql`
  - `erp_logistics_schema.sql`

> `.sql` 파일 중 `*_schema.sql` 이 아닌 파일은  
> 쿼리, 시드, 유틸 스크립트로 간주한다.

---

## 4. 파일별 버전 관리 원칙

- 전체 저장소 버전을 하나로 묶지 않는다.
- **파일 단위 버전(file_version)** 을 사용한다.
- 버전은 Git 태그나 파일명에 넣지 않고,
  **각 파일 헤더에 명시**한다.

### DDL 헤더 예시
```sql
-- Project : ERP Data Guide
-- Repo    : erp-data-guide
-- File    : ddl/erp_core_schema.sql
-- Version : 1.0.3
-- Date    : 2026-01-20
-- Summary : Documents hub 통합 및 문서 코드 표준 확장
```

### Markdown 헤더 예시
```md
---
project: "ERP Data Guide"
repo: "erp-data-guide"
file: "docs/operations-guide.md"
version: "1.0.2"
date: "2026-01-20"
summary: "문서 허브 운영 규칙 및 결정 트리 보강"
---
```

---

## 5. 변경 시 작업 규칙

1. 수정 대상 파일을 선택한다.
2. 해당 파일의 헤더에서:
   - Version 증가 (patch 기준)
   - Date 갱신
   - Summary에 변경 요약 작성
3. Git 커밋 메시지에 변경 파일/의도를 남긴다.

> CHANGELOG.md는 사용하지 않는다.  
> 변경 이력은 Git과 파일 헤더가 담당한다.

---

## 6. ADR (Architecture Decision Record) 운영 원칙

현재 이 저장소는 **설계 진행 단계**이며(서비스 런칭 전), 의사결정이 계속 바뀔 수 있다.  
따라서 ADR은 **지금 단계에서는 작성/유지하지 않고 비워둔다.**

- 설계 결정의 단일 진실 소스(Single Source of Truth)는 `docs/design-decisions-log.md` 이다.
- `adr/` 디렉토리는 유지하되, **기본적으로 비워둔다**(placeholder).
- 향후 설계가 안정화되면(예: 개발 착수/런칭 직전/런칭 후),
  `docs/design-decisions-log.md`에서 핵심 결정만 추려 ADR로 **추출**한다.
- ADR을 생성하는 경우에도 기존 기록을 삭제하지 않고,
  `design-decisions-log`는 계속 “결정 이력의 정본”으로 유지한다.

## 7. 새로운 대화를 시작할 때 (중요)

아래 메시지를 그대로 복사해 새 대화의 첫 메시지로 사용한다.

```text
ERP Data Guide 저장소의 정본을 기반으로 설계를 이어서 진행하고 싶다.

이 저장소에는 다음이 포함되어 있다:
- DDL (erp_*_schema.sql)
- 운영 가이드 / 설계 맥락 문서
- ADR(Architecture Decision Records)

이미 결정된 사항(Project-centric, cost≠payment, documents hub 등)은 재논의하지 말고,
새 요구사항이나 변경이 필요한 부분만 제안해 달라.
```

---

## 7-2. 이 저장소를 다루는 GPT의 역할

이 저장소를 다루는 GPT는  
새로운 설계를 처음부터 작성하는 주체가 아니라,  
이미 기록된 정본을 기준으로 변경 사항을 **부분적으로 반영·병합하는 편집기(Editor)** 로 동작한다.

새로운 요구사항이나 당면한 문제로 인해  
현재 구조의 한계가 드러나는 경우,  
대안 방향이나 구조 변경에 대한 검토·조언은 가능하다.

다만, 이러한 제안은 기존 문서를 대체하거나 축약하는 방식이 아니라,  
기존 설계 위에 변경과 그로 인한 영향을 **누적적으로 반영**하는 형태로 이루어진다.

---

## 7-3. 변경 반영에 대한 기본 원칙

이 저장소의 문서는 설계 과정의 산출물이 아니라,  
설계 자체를 구성하는 **누적 자산**이다.

따라서 변경은 항상 전체 재작성이나 요약이 아닌,  
명시적인 부분 변경과 영향 반영의 형태로 처리한다.

기존 문서가 유지해온 서술의 밀도, 표의 크기, 예시의 풍부함은  
의도된 설계 품질로 간주하며,  
변경과 무관한 내용을 단순화하거나 축약하지 않는다.

## 문서 기록/병합 규칙 (중요)

이 저장소의 문서는 “DDL 산출물”을 넘어, **설계에 도달하기까지의 모든 판단/근거/사용법**을 남기기 위한 것이다.  
따라서 **요약/축약/누락 없이** 내용을 유지하면서도, **최신 설계 기준으로 정본화**하여 일관된 문서를 만든다.

### 1) 문서 구성 원칙: 설명 문서는 4개만 사용 (ADR 제외)

ADR(Architecture Decision Record)을 제외한 **모든 정책/가이드/설명/예시/운영 시나리오**는 아래 4개 파일 중 하나에 반드시 포함한다.

- `design-and-scenarios.md`  
  - 스키마를 “어떻게 써야 하는지”를 보여주는 **업무 시나리오/데이터 입력 흐름/실 입력값 예시**  
  - 입력 순서, FK 연결, 상태 전이, 검증 포인트, 예시 템플릿(표/레코드 서술)을 포함

- `schema-policy.md`  
  - 스키마의 **불변 규칙**: 네이밍/약어/PK 규칙, 관계/제약/인덱스 규칙, 문서 허브(`documents + document_links`) 같은 코어 정책  
  - 코드값(codebook)이나 enum-like 규칙이 있으면 여기에서 정본화

- `operations-guide.md`  
  - 실제 운영자가 수행하는 **운영 절차/점검/재처리/권한/오류 대응**  
  - “데이터 입력 예시” 그 자체는 `design-and-scenarios.md`가 본진이며, operations에서는 운영 액션 관점으로 참조/가이드를 제공

- `design-decisions-log.md`  
  - 최종 결정과 그 이유, 검토한 대안과 기각 사유, 변경 히스토리(무엇이 왜 바뀌었는지)

> 핵심: “내용을 통째로 붙여넣기”가 아니라, **내용의 역할에 따라 4개 문서에 재배치/병합**한다.

### 2) 병합의 대전제

- **축약/요약/삭제 금지**  
  - 표/템플릿/라인 수를 줄이거나, 설명을 짧게 만드는 요약은 금지
- **최신 버전 기준 정본화**  
  - 충돌이 있으면 최신 버전의 규칙/엔티티 구조를 정본으로 삼는다.
- **풍부한 쪽을 기본 형식으로 유지**  
  - 어떤 버전에서 표가 축약되었거나 레코드 수가 줄었으면, **더 풍부한(상세한) 표/형식**을 유지하고 최신 버전의 신규 항목만 추가한다.
- **레거시 운영 전제는 없음**  
  - 과거 문서의 내용은 “운영 레거시”가 아니라 “설계 히스토리”다.  
  - 따라서 과거 엔티티/구조를 “그대로 남겨서 병기”하는 것이 아니라, **의미 있는 디테일/템플릿을 최신 구조로 치환하여 통합**한다.

### 3) Deprecated 처리 규칙 (매우 중요)

> **레거시 운영 전제 없음.** 과거 문서는 “설계 히스토리/아이디어 저장소”일 뿐이며, 실제 운영 레거시를 병기하기 위한 문서가 아니다.  
> 따라서 deprecated 엔티티/명칭은 **본문에 남기지 않는다.**

- 최신 정본에서 **존재하지 않는 테이블/엔티티/필드**는 예시/설명 본문에 남기지 않는다.
- 과거 문서가 담고 있던 **시나리오/디테일/검증 포인트/템플릿(표/레코드 서술 방식/입력 순서)**은 유지하되,
  **반드시 최신 정본 엔티티로 “변환(Rewrite)”한 뒤 병합(Merge)**한다.
- **원문 블록(버전별 원문)을 그대로 부록으로 붙이는 방식은 사용하지 않는다.**
  - “과거 내용 유지”란 **문장/템플릿/체크리스트/표의 구조를 유지하되 최신 구조로 재작성**하는 것을 뜻한다.

예시 치환(대표):
- `payment_documents` / `cost_documents` 등 문서 분리 구조 → **`documents`에 저장 + `document_links`로 연결**
- `domestic_*`, `overseas_*` 등 분리 테이블 구조 → **단일 `rfqs` / `purchase_orders` 체계로 통합(정본)**

> 문장/예시에서 deprecated 명칭이 1회라도 남아있으면, “치환이 덜 된 것”으로 보고 반드시 정리한다.

### 4) 병합 파이프라인: Rewrite → Merge → Verify (필수)

병합 작업은 아래 3단계를 **항상 같은 순서로** 수행한다. (이 순서를 바꾸면 deprecated가 남거나 “원문 모음집”이 되기 쉬움)

1. **Rewrite(변환)**
   - deprecated 엔티티/관계가 등장하는 문장/표/예시를 **최신 정본 엔티티로 재작성**한다.
   - 이 단계에서 “Deprecated → Canon 매핑 표”를 기준으로 일관되게 치환한다.

2. **Merge(병합/재배치)**
   - 변환된 내용을 4개 문서의 역할에 맞게 재배치한다. (통째로 붙여넣기 금지)
   - 중복되는 내용이 있으면 **더 풍부한 설명/템플릿을 정본으로 삼고**, 다른 버전의 추가 디테일만 합친다.

3. **Verify(검증)**
   - 금칙어(예: `domestic_`, `overseas_`, `payment_documents`, `cost_documents` 등) 검색 결과가 **0건**인지 확인한다.
   - 동일 의미 중복이 과도한지 확인하고, 필요하면 “추가 디테일만 병합” 형태로 정리한다.


### 5) 재배치/병합 체크리스트

병합/정리 시 반드시 아래를 확인한다.

1. 새 버전에서 바뀐 정본 구조/정책을 파악하고, 충돌 지점을 목록화한다.
2. “더 풍부한 서술/표/템플릿”을 기준으로 형식을 선택한다.
3. 과거 문서에서 유의미한 디테일을 **최신 엔티티로 치환**하여 통합한다.
4. deprecated 명칭이 문서 본문에 남지 않도록 전체 검색 후 제거/치환한다.
5. 내용의 역할에 따라 4개 문서에 재배치한다(통째로 붙여넣기 금지).
6. 결정/대안/기각 사유는 반드시 `design-decisions-log.md`에 남긴다.
