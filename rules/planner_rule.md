# 기능 기획 역할, 책임, 산출물 완료 기준

---

# 1. 목적

본 문서는 시스템 및 서비스 기능 개발에서 기능 기획이 정의해야 할 범위와 산출물 완료 기준을 명확히 하기 위한 문서이다.

기능 개발은 화면, 데이터, 상태, 업무 규칙, 예외 처리가 함께 맞물려 동작한다. 따라서 개발 착수 전 기능 기획 산출물은 기능의 외부 동작과 데이터 변화, 상태 변화를 확인할 수 있는 수준으로 작성되어야 한다.

---

# 2. 기능 기획의 역할 정의

시스템 및 서비스 기능 기획은 다음 범위를 포함한다.

> 기능 기획은 시스템의 외부 동작, 데이터 의미, 상태 변화, 업무 규칙을 정의하는 역할이다.

본 문서에서 말하는 기능 기획은 화면 정의를 포함하여, 화면 밖의 데이터, 상태, 업무 규칙까지 함께 정의하는 역할을 의미한다.

기능 기획 산출물은 다음을 명확히 해야 한다.

- 무엇을 만들 것인가
- 사용자는 어떤 흐름으로 기능을 사용하는가
- 어떤 데이터가 사용되는가
- 데이터는 어떻게 생성, 조회, 수정, 삭제되는가
- 어떤 상태에서 어떤 상태로 변화하는가
- 어떤 업무 규칙이 적용되는가
- 정상 상황과 비정상 상황에서 각각 어떻게 처리되는가

---

# 3. 기능 기획과 개발의 역할 구분

## 3.1 기능 기획의 책임

기능 기획은 반드시 다음을 책임진다.

- 기능 목적과 범위 정의
- 사용자 흐름 정의
- 화면별 동작 정의
- 데이터 의미 정의
- 데이터 생성, 변경, 삭제 규칙 정의
- 상태 정의 및 상태 전이 정의
- 업무 규칙 정의
- 예외 및 오류 상황 정의
- 시나리오 완결성 검증
- 기능에 필요한 입력값, 결과값, 오류 메시지, 처리 조건 정의

---

## 3.2 개발의 책임

개발은 다음을 책임진다.

- 기술적 구현 방식 결정
- DB 구조 설계
- API 설계 및 구현
- 서버, 프론트엔드, 인프라 구현
- 성능 및 안정성 확보
- 보안 처리
- 기술적 구현 가능성 검토

---

## 3.3 중요한 경계

기능 기획과 개발의 책임 경계는 다음과 같이 구분한다.

> 무엇을 만들지 → 기능 기획 책임  
> 어떻게 동작해야 하는지 → 기능 기획 책임  
> 어떻게 구현할지 → 개발 책임  

즉, 개발은 정의된 동작을 구현한다.  
정의되지 않은 동작, 상태, 데이터, 예외를 개발이 임의로 결정하지 않는다.

개발 과정에서 핵심 동작을 해석해서 결정해야 하는 상태라면 개발 착수 기준을 충족하지 못한 것으로 본다.

---

# 4. 검증의 역할 구분

## 4.1 기능 기획 검증

기능 기획 산출물은 다음을 검증한 상태여야 한다.

- 흐름이 중간에 끊기지 않는가
- 상태가 일관적으로 변화하는가
- 입력 데이터와 결과 데이터가 명확한가
- 데이터 생성, 변경, 삭제 기준이 명확한가
- 정상 흐름 외의 대체 흐름이 정의되어 있는가
- 오류, 중복, 권한, 상태 불일치 상황이 검토되어 있는가
- 기능 종료 후 최종 상태가 명확한가

---

## 4.2 개발 검증

개발은 다음을 검증한다.

- 구현 가능성
- 기술적 제약
- 성능 이슈
- 보안 이슈
- 기존 시스템 구조와의 충돌 여부

---

## 4.3 핵심 원칙

> 기능 기획 산출물은 검증된 상태로 제출되어야 한다.  
> 개발은 기능 기획의 완성도를 대신 채우는 것이 아니라, 구현 가능성을 검토한다.

검증은 머릿속 판단이 아니다.  
검증은 다른 사람이 문서를 보고 같은 흐름, 같은 상태, 같은 결과를 재현할 수 있어야 한다.

---

# 5. 기능 기획 산출물 구성

기능 기획은 다음 산출물로 구성된다.

- 기능 정의
- 사용자 흐름
- 화면 정의
- 데이터 정의
- 상태 정의
- 업무 규칙
- 시나리오 및 예외 케이스
- 입출력 요구사항

여기서 입출력 요구사항은 API를 직접 설계한다는 의미가 아니다.  
기능이 동작하기 위해 필요한 입력값, 결과값, 오류 상황, 상태 변화, 데이터 처리 조건을 정의한다는 의미이다.

# 7. 실무 산출물 명칭과 포함 기준

실무에서는 조직이나 프로젝트에 따라 산출물 명칭이 다를 수 있다.
본 문서에서는 특정 문서명을 강제하지 않는다.

다만 어떤 문서명을 사용하더라도, 기능 개발에 필요한 정의 항목은 누락되지 않아야 한다.
아래 표는 일반적으로 사용되는 산출물 명칭과, 해당 산출물에 포함되어야 하는 기능 기획 정의 항목을 연결한 기준이다.

| 실무 산출물명 | 포함되어야 하는 기능 기획 정의 |
|---|---|
| 요구사항 정의서 | 기능 목적, 사용자, 범위, 제외 범위, 제약, 성공 기준 |
| 기능 정의서 | 기능 동작, 처리 조건, 업무 규칙, 상태 변화, 예외 처리 |
| 화면 설계서 / 화면 정의서 | 화면 항목, 입력값, 버튼 동작, 화면 이동, 오류 메시지, 화면 진입 및 이탈 조건 |
| 유스케이스 / 시나리오 | 시작 조건, 입력 데이터, 사용자 행동, 처리 로직, 상태 변화, 데이터 변화, 종료 상태, 대체 흐름 |
| 데이터 정의서 | 데이터 항목, 의미, 출처, 생성 기준, 변경 기준, 삭제 또는 비활성화 기준, 데이터 관계 |
| 상태 정의서 | 상태 목록, 상태 의미, 최초 상태, 최종 상태, 전이 조건, 상태별 가능 행동, 상태별 불가능 행동 |
| 업무 규칙서 | 계산 규칙, 승인 조건, 제한 조건, 권한 조건, 중복 처리 기준, 취소/수정/삭제 가능 조건 |
| 예외 케이스 목록 | 입력 오류, 상태 오류, 중복 요청, 권한 문제, 데이터 없음, 이미 처리된 데이터, 실패 처리 |
| 입출력 요구사항 정의서 | 입력값, 결과값, 오류 응답, 처리 조건, 상태 변화, 데이터 처리 조건 |

문서명은 프로젝트 상황에 맞게 달라질 수 있다.
중요한 것은 문서명이 아니라, 기능이 어떻게 동작하고 데이터와 상태가 어떻게 변하는지 확인 가능한 수준으로 정의되어 있는지이다.

# 8. 시나리오, 유스케이스의 정의

## 8.1 시나리오의 의미

시나리오는 단순 흐름이 아니다.

> 시나리오는 데이터와 상태가 변화하는 완결된 흐름이다.

---

## 8.2 반드시 포함해야 하는 요소

모든 시나리오는 다음을 포함해야 한다.

1. 시작 조건
2. 입력 데이터
3. 사용자 행동
4. 처리 로직
5. 상태 변화
6. 데이터 생성 또는 변경
7. 결과
8. 종료 상태
9. 대체 흐름 또는 실패 흐름

---

## 8.3 잘못된 시나리오

저장 버튼 클릭 → 저장됨

이 흐름은 다음이 빠져 있기 때문에 충분한 기획으로 볼 수 없다.

- 무엇을 저장하는지
- 저장 전에 무엇을 검증하는지
- 어떤 데이터가 생성 또는 변경되는지
- 저장 후 상태가 무엇인지
- 저장 실패 시 어떻게 처리하는지

---

## 8.4 올바른 시나리오

수량 입력 →  
수량 > 0 검증 →  
주문금액 = 수량 * 단가 계산 →  
order.status = DRAFT →  
주문 데이터 저장 →  
저장 성공 메시지 표시 →  
상세 화면 이동

이 시나리오는 입력, 검증, 계산, 상태 변화, 데이터 저장, 결과 화면이 연결되어 있다.

---

# 9. 상태 변화 시나리오

## 9.1 원칙

취소, 수정, 삭제, 재처리, 상태 변경은 예외가 아니다.  
시스템에서 상태가 바뀌는 지점은 핵심 시나리오이다.

> 상태가 바뀌는 모든 지점은 사전에 검토되어야 한다.

---

## 9.2 반드시 검토해야 하는 상태 변화 축

### 9.2.1 생성 Create

- 어떻게 생성되는가
- 누가 생성하는가
- 생성 직후 상태는 무엇인가

### 9.2.2 수정 Update

- 수정 가능한가
- 언제까지 수정 가능한가
- 무엇이 바뀌는가
- 수정 후 상태가 바뀌는가

### 9.2.3 취소 Cancel

- 취소 가능한가
- 누가 취소할 수 있는가
- 취소 시 되돌리는 데이터는 무엇인가
- 취소 후 상태는 무엇인가

### 9.2.4 삭제 Delete

- 실제 삭제인가
- 논리 삭제인가
- 참조 데이터가 있을 때 삭제 가능한가
- 삭제 후 조회, 통계, 이력에는 어떻게 반영되는가

### 9.2.5 상태 변경 Status Transition

- 어떤 상태에서 어떤 상태로 바뀌는가
- 상태 변경 조건은 무엇인가
- 상태 변경 제한은 무엇인가
- 상태 변경 이력은 남는가

### 9.2.6 재처리 및 중복 처리

- 같은 요청을 두 번 하면 어떻게 되는가
- 이미 처리된 건을 다시 처리하면 어떻게 되는가
- 재처리가 가능한 조건은 무엇인가

### 9.2.7 실패 및 롤백

- 중간에 실패하면 어떻게 되는가
- 일부만 성공하면 어떻게 되는가
- 기존 데이터는 유지되는가
- 변경된 데이터는 되돌리는가

---

# 10. 예외 및 오류 케이스

## 10.1 원칙

예외가 없는 기능은 없다.

다만 취소, 수정, 재처리, 상태 변경은 예외 케이스로 밀어둘 대상이 아니다.  
이들은 별도의 상태 변화 시나리오로 사전에 정의해야 한다.

---

## 10.2 반드시 포함해야 하는 예외

- 입력 누락
- 잘못된 입력
- 상태 오류
- 중복 요청
- 권한 없음
- 데이터 없음
- 이미 처리된 데이터
- 시스템 처리 실패

---

## 10.3 예시

입력 누락 → 오류 메시지 표시 → 기존 입력값 유지  
상태 오류 → 저장 불가 → 현재 상태 안내  
중복 요청 → 추가 처리하지 않음 → 기존 처리 결과 안내  
권한 없음 → 처리 불가 → 권한 오류 안내

---

# 11. 데이터와 시나리오의 관계

## 11.1 핵심 원칙

> 데이터가 없는 흐름은 기획으로 인정하지 않는다.

입력 데이터 →  
검증 →  
처리 로직 →  
상태 변화 →

종료 상태

# 12. 잘못된 기능 기획과 올바른 기능 기획

## 12.1 잘못된 기능 기획

- 흐름만 존재
- 데이터 없음
- 상태 없음
- 예외 없음
- 종료 조건 없음
- 개발 과정에서 해석해야 하는 부분이 많음

---

## 12.2 올바른 기능 기획

- 흐름 존재
- 데이터 정의
- 상태 정의
- 상태 전이 정의
- 업무 규칙 정의
- 예외 및 오류 정의
- 완결된 시나리오 존재

---

# 13. 개발 착수 전 보완 요청 기준

다음 중 하나라도 해당하면 개발 착수 전에 기능 기획 보완이 필요하다.

- 기능의 시작 조건 또는 종료 조건이 불명확한 경우
- 화면 흐름만 있고 데이터 정의가 없는 경우
- 상태 정의 또는 상태 전이가 없는 경우
- 생성, 수정, 취소, 삭제, 재처리 기준이 없는 경우
- 입력 오류, 중복 요청, 권한 문제, 상태 오류가 검토되지 않은 경우
- 저장, 변경, 삭제되는 데이터가 명확하지 않은 경우
- 핵심 동작에 대해 해석이 여러 갈래로 나뉠 수 있는 경우

기능 기획 보완 후 개발은 구현 가능성, 기술적 제약, 일정 영향을 검토한다.

---

# 14. 자주 발생하는 오해

## 오해 1

“생각해서 검증했다.”

→ 검증은 문서로 재현 가능해야 한다.

---

## 오해 2

“정의가 부족한 부분은 개발 단계에서 결정하면 된다.”

→ 정의되지 않은 동작, 상태, 데이터, 예외는 개발이 임의로 결정하지 않는다.

---

## 오해 3

“이상 없다.”

→ 검증 과정 없이 내린 판단은 검증으로 인정되지 않는다.

---

## 오해 4

“취소, 상태 변경, 재처리 같은 특이 케이스는 발생하면 그때 답하면 된다.”

→ 모든 미래를 예측하라는 뜻이 아니다.  
→ 다만 상태가 바뀌는 모든 지점은 사전에 검토되어야 한다.

시스템에서 취소, 수정, 재처리, 상태 변경은 예외가 아니라 핵심 시나리오이다.

---

# 15. 최종 기준

기능 기획은 다음을 만족해야 한다.

- 흐름 완결성
- 데이터 정의
- 상태 정의
- 상태 전이 정의
- 업무 규칙 정의
- 예외 및 오류 정의
- 검증 가능한 시나리오

---

# 16. 최종 정의

> 기능 기획은 문서가 아니라, 정의된 시스템 동작이다.

> 완성된 기능 기획이란 화면이 그려진 문서가 아니라, 개발 과정에서 핵심 동작을 추측하지 않아도 되는 문서이다.
